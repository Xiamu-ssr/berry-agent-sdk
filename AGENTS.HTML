Berry Agent 平台对齐页

唯一入口：本页。AGENTS.md 只跳转到本页。docs/anthropic-managed-agents-notes.md 是历史推导记录,本页是当前事实。

一句话

Berry 是 一套 4 层 agent 基础设施:SDK 提供 agent 内核 + Worker 提供单机 runtime daemon + a8s 提供集群 control plane + 上层产品(berry-claw 等)用这套设施做面向用户的 agent 应用。

SessionStore 远程实现(对象存储 / Postgres),解锁 worker 间真正的 session 漂移。等真实部署场景驱动。

4 层架构

Layer 4 — Products 面向用户的 agent 产品。每个产品决定自己的用户交互(聊天 UI / 命令行 / IDE 插件 / 手机 app / Slack bot / ...)。不存在于本 monorepo(berry-claw 是第一个,独立仓库)。
Layer 3 — Control Plane (a8s) 集群级调度:接收"创建 agent"请求,根据 capability/capacity 决定调度到哪个 worker,管理 lease 和 wake 的分配。@berry-agent/a8s 提供类;@berry-agent/a8s-server 把它服务化成可独立部署的进程,暴露 HTTP API + 内嵌运维 UI。
Layer 2 — Worker 单机 runtime daemon。一个 worker 进程 = 一个资源容器,跑 N 个 agent 的 brain。负责 lease 续约、heartbeat、把 agent 任务路由到本地 brain。@berry-agent/worker 提供类;@berry-agent/worker-daemon 把它服务化成可独立部署的进程,主动出网注册到 a8s。
Layer 1 — SDK Runtime (Anthropic 4+1) 单 agent 内核:brain (ManagedAgentRuntime) + session (event log 事实源) + hands (能力抽象) + execution environment (执行点) + safety (guard + approval)。可独立 import 当库用,无服务化要求。

和 Anthropic 4+1 图的映射

Anthropic 图是单 agent 内部架构。它的 5 个组件全部在 berry 的 Layer 1 (SDK) 实现。

映射:Harness = ManagedAgentRuntime;Session = file/event-log SessionStore;Tools/MCP = Hand;Sandbox = ExecutionEnvironment;Orchestration = RuntimeOrchestrator (lease/wake/worker)。

多 agent 调度不在原图里。berry 加了 Layer 2 (Worker) + Layer 3 (a8s) 来支持集群部署,这是 Anthropic 图的合理扩展,不是替代。

不可变原则

  • 事实源唯一:messages.json = LLM 上下文;events.jsonl = UI/审计 timeline;orchestration 元数据 = SQLite/Postgres;agent 项目文件 = 产品自己管(GitHub 等)。这四种数据**各管各的存储**,互不复制。
  • Brain 无状态:Brain = "session 引用 + 短暂的进程"。任何时刻可以杀掉一个 brain 进程,起一个新的,只要它能读到那份 session 就能接着跑。Brain 不持有不可恢复的内存状态。
  • Hand 配置不绑机器:Hand 的"在哪里跑"由 ExecutionEnvironment 决定,跟 brain 跑哪儿无关。Brain 在云、hand 在本地完全合法。
  • Lease 单点持有:每个 agent 同一时刻只有一个 brain 持有它的 lease,数据库保证。Failover 通过"老 worker 死了 → lease 过期 → 新 worker 抢到"实现,不需要 brain 间通信。
  • Agent 间通信走 control plane,不走 brain 直连。Team / 跨 agent 调用 / 共享数据,3 种方式全部不要求 agent 同 worker。
  • a8s 只存元数据,不存机密:a8s 不持有 SSH key、不持有 LLM API key、不当密钥网关。它存 orchestration 元数据 + 集群级配置(models template 的 provider/model/tier 形状)。API key 物理上由每个 worker 自己持有(worker.json 内联,或 worker 启动时从 a8s 拉 template 后存在自己机器上)。a8s 被攻破 ≠ 所有 worker 的密钥泄漏。
  • 配置单向流动:operator 在 a8s UI 配一次 models template → 每个新 worker 在 register 时拉取并落到本机。没有反向:worker 不回写配置到 a8s,a8s 不 push 配置到 worker。新 worker 加入 = 主动出网 register + pull,a8s 永远是被连接方。
  • 能力注入靠 label,不靠耦合:berry-admin 不是 a8s-server 直接 addHand 的。a8s-server 只在 spec 上盖 labels.role='a8s-admin';真正 mount agent 的 worker 在自己的 resolveSpec 里看到这个 label,seed 默认 AGENTS.md + ops skills 并把 a8s URL/token 注入该 agent 的执行环境(让它的 berry-a8s-ops CLI 能认证)。a8s-server 不 import 任何运维代码 — 它是基础设施,berry-admin 是跑在它上面的产品。同一机制服务于 team-mode(labels.team)和 machine-mode(labels.machines)。
  • 运维是知识不是内建工具:操作集群(看状态、drain/evict、加 worker/机器)走 berry-a8s-ops CLI + a8s-ops skill,不做成每个 agent 的硬编码 tool。执行层(Hand/env)不背运维语义;berry-admin 用通用 shell Hand 跑 CLI。加一个运维操作 = CLI 加一个子命令 + skill 加一行,agent 的 tool 面不变。
  • env 只属于"落地机器"的工具:workspace 工具(file/shell/search)+ machine exec 绑 ExecutionEnvironment 的 executor;web / API / skill / cli 不持 env(web 是无 env Hand;cli 寄生在执行它的 Hand 的 env 子进程里)。本机不是特殊装配,只是一台贴了 primary 标记的普通 env,agent 不感知 env。
  • skill 格式是统一契约,产品不转译:SKILL.md(frontmatter + 正文)由 SDK 定义,a8s 存储(物理在 worker 的 agent home),所有产品共同遵循。产品在 skill 之上挂 market 视图(分类/评分),但不转译 skill 本体 —— 否则 agent 自蒸馏的、a8s 侧 seed 的 skill 会和产品格式打架(最隐蔽的多事实源)。
  • 新增持久化/transport/domain 数据结构:先写 zod schema,再推导类型。
  • 直接 tool 会被包成 SDK-owned Hand;能力暴露和执行走统一 policy/audit。
  • 默认 command/MCP stdio 环境不带长期密钥;密钥通过 CredentialStore 或显式 scoped env。berry-admin 的 a8s token 是显式 scoped env 的一例(仅注入 a8s-admin label 的 agent)。

Layer 4 — Products

本仓库不含 Layer 4 包。berry-claw 是第一个产品(独立仓库),定位为瘦 BFF:无自己的 engine,经 @berry-agent/client 远程连 a8s(所有产品 engine 都走 a8s,不做单机)。BFF 持 token 不下发前端,前端 WS ↔ BFF ↔ a8s SSE。当前过渡态:client 依赖 + a8s-client 脚手架已就位,但 AgentManager 仍在 in-process(new Worker());切换为 client-backed(8 个 host + 测试套件重写)是进行中的 C 工作。SDK 侧所需 a8s API(配置面、session 读写、流式 send)已全部备齐。

当前部署形态

形态 A — 全本地(开发 / 单机产品)

所有东西在一个 Node.js 进程里:产品 + a8s + worker + brain。这是 berry-claw 现在的形态。适合开发、小规模、个人使用。Worker 类内嵌,无需 HTTP 协议。

npm install -g @berry-agent/claw-server@alpha
berry-claw start
# 单进程跑 N 个 agent,关进程全没

形态 B — 单机或多机集群(已可用)

1 个 berry-a8s 进程 + N 个 berry-worker 进程(可以在同机也可以跨机) + 共享 SQLite(单机)或 Postgres(跨机)。Worker 主动出网注册到 a8s,周期 heartbeat,接收 a8s 派来的任务。Worker 进程崩了 → systemd 拉起同 workerId → a8s 在 register 响应里告诉它要再 mount 哪些 agent → 从机器级 /var/berry/agents/<id> 自动 mount,数据零移动(参见"失效模式与恢复")。

# 服务器 A:启动 a8s(纯 control plane,不自带 worker/agent)
sudo mkdir -p /var/berry/a8s
berry-a8s start --port 8080 \
  --store sqlite:///var/berry/a8s/orch.db \
  --admin-token "$ADMIN_TOKEN" \
  --advertise-url https://a8s.example.com
# 然后浏览器打开 /ui:Settings 里填供应商 key + 拉模型列表配好 models,
# 再起至少一个 worker(下面),最后一键 Bootstrap admin agent。
# 服务器 B:写 worker 配置(指定 a8s URL + admin token + 数据布局)
sudo mkdir -p /var/berry/workers/worker-b /var/berry/agents
cat > /var/berry/workers/worker-b/worker.json <<EOF
{
  "workerId": "worker-b",
  "port": 7100,
  "bindHost": "10.0.1.10",
  "a8s": "https://a8s.example.com",
  "adminToken": "$ADMIN_TOKEN",
  "capacity": 16,
  "heartbeatTtlMs": 30000,
  "dataRoot": "/var/berry/workers/worker-b",
  "agentsRoot": "/var/berry/agents",
  "machine": "machine-b",
  "registry": { ...provider/model/tier... }
}
EOF

# 启动 worker
berry-worker start --config /var/berry/workers/worker-b/worker.json

# 任何客户端创建 agent(workspace 用 bare id,worker 自动解析到 agentsRoot)
curl -X POST https://a8s.example.com/v1/agents \
  -H "authorization: Bearer $ADMIN_TOKEN" \
  -H 'content-type: application/json' \
  -d '{"spec":{"agentId":"coder","workspace":"coder","model":"tier:strong"}}'

形态 C — 跨机灾难恢复(刻意暂不做)

形态 B 已经解决了 ~90% 的失效场景(失效模式 中前两行)。剩下的"机器整个死"目前需要 operator 手动 rsync agent home 到目标机 + 调 migrateAgent(preferredMachine: null)。

为什么 alpha 阶段刻意不自动化:

  • 无共享盘的跨机自动恢复 = 需要某种地方存 agent home 的副本。最自然的实现(a8s 周期收 worker tarball,失败时推给目标 worker)让 a8s 变成数据节点(原本只存元数据),并引入 RPO/RTO/磁盘容量/备份频率四个新维度的参数。
  • 没有真实部署数据反推合理频率(每秒?每分?每小时?触发条件?压缩?)。盲拍出来的方案大概率要重做。
  • 形态 B 的 same-machine 失效占 deploy/OOM/bug 的绝大多数;真"机器死"在小集群一年也未必出一次。先发车,等真痛点。

未来选项(任择其一,都能解):远端 SessionStore 实现(对象存储 / Postgres)、共享文件系统(NFS / EFS)、CSP 块存储跨机重新挂载。SDK 的 SessionStore / AgentHome 都是接口,实现可换。

形态 D — Cross-worker Team(已可用)

Leader agent 在 worker A,teammate agent 在 worker B,两边通过 a8s 间接通信:

  • Leader → teammate(同步):leader 的 message_teammate 工具走 POST /v1/agents/<tm>/send,a8s 转发到 B,等返回。
  • Teammate → leader(异步):teammate 的 message_leader hostTool(worker daemon 在 labels.team===true 时自动注入)走 POST /v1/wakes/schedule,a8s 的 wake 调度器把消息当成 leader 的下一个 turn 投递。

没有 brain 直连。Failover、跨机部署、消息持久化全部继承 a8s + wake 的现成保证。Team-side worklist 等更丰富的协作原语是后续工作。

运维 UI

berry-a8s 启动后,浏览器打开 http://<a8s host>:<port>/ui 即出现单页运维台。React + Vite + Tailwind 构建,产物内嵌在 @berry-agent/a8s-server 里,零外部 CDN。首次访问要求贴 admin token,存在 localStorage,之后所有调用走 Authorization: Bearer ...。设计意图:第一次 berry-a8s start 之后,整个集群从浏览器即可运营,无需再用 CLI flag 或 curl。

  • Cluster:worker 数量、容量、agent 数、uptime。聚合自 /v1/operator/cluster。
  • Workers:列表 + drain/undrain/evict 按钮 + 生成 worker join 脚本(弹窗供操作员复制粘贴,内嵌 admin token)。
  • Agents:列表 + Create agent 表单(model 选项来自 models template 的 tier/model;Grant machines 多选 → 写 labels.machines,给 agent 注入对应机器的 exec 工具)→ 点 agent 看 sessions → 点 session 看 SSE 实时事件流。
  • Machines:注册的机器列表(state / platform / 可代理的 MCP / heartbeat)+ Add machine 按钮(弹出 connector 安装脚本,内嵌 admin token)。
  • Settings:Models 配置表单(选供应商 preset → 填 key → "拉模型列表"经 a8s 代理供应商 /models → 勾选模型 → 配 tier;JSON 退为 Advanced 模式)+ admin-agent 自举卡片(一个按钮把 berry-admin 通过通用 createAgent 调度到 active worker —— a8s 已无 --admin-agent flag,这是唯一路径)。
  • Admin Chat:跟 berry-admin 聊。"how is the cluster?" / "drain worker X" / "how do I add a worker?" / "what machines do I have?" / "add a machine" 都能说出来,admin 通过 shell 跑 berry-a8s-ops <cmd>(配 a8s-ops skill)完成。

机器层:机器即 Environment / Hand(已落地)

"给一台机器装 worker、运维它"不再靠复制脚本或固定命令清单的"连接器"(固定 RPC = 不灵活,正是要逃离的反模式),而是把机器变成 agent 能操作的通用执行面。设计与推导见 docs/machine-layer.md。核心:

  • 每台机器 = 一个 ExecutionEnvironment。机器侧 berry-machine connector(@berry-agent/machine-connector)主动出网注册到 a8s,服务 /exec + /mcp/invoke。它不跑 agent brain(区别于 worker),只借出执行面 + 本机 MCP 能力。
  • a8s 是代理,且 MCP-agnostic:agent 的机器 Hand 调 a8s(admin-scoped,worker 本就持有),a8s 持有 machine token 转发到机器的 /exec 或 /mcp/invoke。机器凭证永不离开 a8s;MCP 的持久 stdio 连接只在机器本地,a8s 只转发一问一答 —— 和控制面其他部分"代理连接、不发放钥匙"同一立场。
  • "选 Hand = 选机器":agent spec 带 labels.machines='id1,id2',worker 的 resolveSpec(withMachineHostTools,与 cluster-admin 同一注入通道)给它注入每台机器的 machine_<id>_exec 工具,外加本机每个 MCP 工具投影成 machine_<id>__<server>_<tool>(机器 + MCP 双命名空间,对齐 Claude Code 的 mcp__ 但加机器前缀)。主环境保持单数,不把核心 executionEnvironment 复数化。
  • "装 worker" 是 skill,不是端点 API:install-worker SKILL.md(随 berry-admin seed)教 agent 用通用 exec 自己拼命令装 worker(registry:null 拉 template,不落 key)。worker 退化成 agent 用机器 Hand 装出来的产物之一。这废弃了原 F6(worker-daemon 固定运维端点)。
  • OS 差异自动吸收:命令在目标机真实 shell 跑,Mac/Linux 差异是命令本身的事,无需为每个 OS 写一套工具。
  • 两道安全闸:ManagedToolGuard(允不允许这条命令,决策层)+ Environment 的 isolationPolicy(本机物理边界)。机器 connector 默认裸 NodeExecutor,生产应前置 OS sandbox 或低权用户。

首次接入仍需人工一次(Add machine → 在目标 host 跑安装脚本),之后 agent 永久接管,a8s 不持有 SSH key。Hand 的四层来源(谁写代码):L0 通用工具 SDK 自带(零代码);L1 现成 MCP 填 .mcp.json(零代码);L2 全新能力写标准 MCP server(一次性,跨平台复用);L3 产品装机预置 + UI 加 MCP。终端用户永不写代码。本机 MCP 已落地:connector 盘点本地 .mcp.json、连上 MCP server(stdio 保持原样)、把工具投影成机器 Hand,a8s 只转发一问一答 —— 这是"云端 a8s 取代本地 Engine"的关键一环。仍待落地:MCP 工具过多时的二等渐进披露(SDK 投影层,对所有 Hand 通用);Environment 池 / Hand 池 / agent 蓝图池的注册表与 UI。详见设计文档。

三个池(Environment / Hand / 蓝图)

a8s 的"可复用市场"直觉成立,但复用粒度按类型不同:Environment 池(机器/容器配方,无状态可复用 —— 机器层是它第一个成员)、Hand 池(能力打包,无状态可复用;比 Environment 池大,含 team、machine exec、web 这种 Hand)、Agent 蓝图池(system prompt + 选定 Hand + 环境配方的"起点配方",配方无状态、实例化出全新独立 session)。Session 不入池:它是有状态历史(messages.json + events.jsonl,绑机器目录),共享实例 = 身份混乱 + 抢 lease(违反 lease 单点持有)。市场卖的是配方(蓝图),不是存档(session 实例)。今天的 labels.role / labels.machines 注入已是 Hand 池的原始版。详见 docs/machine-layer.md。

判断一段代码该放哪

问题答案
影响 agent turn、context、tool loop、resume?放 Layer 1 (SDK)。
定义持久化 agent 数据结构?放 Layer 1,并先写 zod schema。
关于单台机器上 N 个 agent 的 runtime mount 生命周期?放 Layer 2 (worker)。
关于多个 worker 之间的调度/lease/failover?放 Layer 3 (a8s)。
关于用户怎么连接、UI 怎么展示、auth、订阅?放 Layer 4 (产品)。
关于真实容器/远程 worker 部署?实现 ExecutionEnvironment 接口(Layer 1 契约,worker 调用)。

目录事实源

Berry 把生产部署的所有数据组织在一个 berry root(默认 /var/berry/)下。关键设计:agent home 是机器级路径(/var/berry/agents/<id>/),不归任何 worker 私有 — worker 只持有 lease 来"挂载"。worker 自己的状态(observe.db、creds.json)才放 /var/berry/workers/<workerId>/。

/var/berry/                                  ← berry root (用户可改)
├── a8s/                                     ← a8s control plane 数据
│   ├── orch.db                              ← SQLite orchestration store
│   │                                          (runtime_workers / runtime_leases / runtime_wakes)
│   └── a8s.log
│
├── workers/                                 ← worker 进程自己的状态
│   ├── <workerId>/                     ← e.g. worker-b
│   │   ├── observe.db                       ← worker 的 observe SQLite
│   │   └── creds.json                       ← credential store
│   └── <otherWorkerId>/                 ← 同机第二个 worker,各管各的
│
└── agents/                                  ← agent home(机器级,worker 不私有)
    └── <agentId>/                       ← e.g. coder
        ├── agent.json                       ← agent 不变身份 + 当前模型选择
        ├── AGENTS.md                        ← 系统提示(用户写)
        ├── MEMORY.md                        ← 长期记忆(agent 写)
        ├── .mcp.json
        ├── skills/
        ├── memory/
        └── sessions/<sessionId>/
            ├── messages.json                ← LLM 上下文事实源(compact 后稳定)
            ├── metadata.json
            └── events.jsonl                 ← append-only timeline(审计 + UI)

<project-root>/                          ← agent 工作的项目目录(产品/用户提供)
├── AGENTS.md                                ← project-level 上下文
└── .berry/                                  ← SDK 在项目里的私有目录
    ├── team.json
    ├── messages.jsonl
    ├── worklist.json
    └── safety.json

数据归属:

  • a8s 只读写 /var/berry/a8s/(元数据,几 KB ~ 几 MB)。它不碰任何 agent home 数据。
  • Worker 进程状态(observe.db、creds.json)绑在 /var/berry/workers/<workerId>/。同机多 worker 各自一个子目录,文件系统权限隔离。
  • Agent home 放在 /var/berry/agents/<agentId>/,**对同机所有 worker 可见**。Worker 持有 lease 时挂载,lease 释放则可被同机其他 worker 接管。**Lease 在 orch.db 里全局唯一**,数据竞争不会发生。
  • 跨机 failover(机器死)目前不自动,需要把 agent home 同步到目标机器(rsync / 对象存储 / 远端 SessionStore)。常见的"worker 进程崩"路径完全不需要数据搬运,见下。

失效模式与恢复

Worker 怎么"死",对应不同的恢复路径。berry 的 layout 专门为常见路径优化,罕见路径诚实地交给运维。

失效频率数据状态恢复路径RTO
worker 进程崩(deploy / OOM / bug) 常见 磁盘完好 systemd Restart=always 拉起同一 workerId 的新进程 → 重新注册到 a8s → a8s 在 register 响应里告诉它 ownedAgents → worker 从 /var/berry/agents/<id>/agent.json 读 spec 自动 mount。零运维,数据零移动。 秒级
同机其他 worker 接管(多 worker 部署) 不常见 磁盘完好 lease TTL 过期 → a8s 释放 → 同机另一 worker 通过 scheduler 的 same-machine 亲和力(labels.machine 匹配 + preferredMachine hint)被调度 → 它也能读 /var/berry/agents/<id>/ → mount。零数据移动。 分钟级(TTL)
跨机 failover(机器死) 罕见 磁盘失联 需要 agent home 已在共享存储,或 operator 手动 rsync 后 migrateAgent(preferredMachine: null 强制换机)。alpha 阶段:lease 自动释放,a8s 标记 agent stranded。未来:远端 SessionStore 解锁自动恢复。 人工介入

scheduler 通过 labels.machine(默认 = os.hostname())识别同机 worker;createLeastLoadedScheduler 收到 preferredMachine 时先在同机子集找可用 worker,找不到再回落全局。
