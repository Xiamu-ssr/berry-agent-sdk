Berry Agent SDK 对齐文档

本文件是 SDK 仓库的人类说明、架构约定和 agent 协作入口。README.md 和 AGENTS.md 只保留到本文档的引用，避免多份事实源漂移。

定位

Berry Agent SDK 是用于构建长期运行、可恢复、可审计、可接入工具/MCP/Skill 的 TypeScript Agent SDK。它不是产品 UI，也不保存产品端实例列表、桌面壳状态或业务导航。

SDK 负责
agent 生命周期、provider 调用、messages/events、session view hydrate、compaction、tool loop、MCP adapter、Skill loader、PromptPack、Memory、Safety、Observe、项目共享布局。
产品负责
选择 agent home 根目录、实例管理、用户交互、前端布局、产品事实展示、跨设备连接、发布包和平台壳。
唯一事实源
messages.json 是 LLM 推理上下文事实源；events.jsonl 是 UI/审计/历史 timeline 事实源。

重构北极星：Managed Agent Harness

目标不是继续给产品层止血，而是把 Berry Agent SDK 收拢成完整的 managed-agent runtime。参考 Anthropic managed agents 的边界：brain 不直接拥有 hands；Harness 连接 Session、Tools/MCP、Sandbox 和 Orchestration。

Source: Anthropic Engineering

对 SDK 的翻译：SDK 是图中间的 Harness 加左侧 Session 的事实源，同时定义 Tools/MCP、Sandbox、Orchestration 的稳定接口。宿主产品可以提供具体实现，但不重新定义 agent turn 的语义。

Tools / MCP / Hands统一 capability contract；MCP、shell、filesystem、browser、remote sandbox 都是 hand，不散落在产品层。
Sessionappend-only event log、messages、metadata、approval、resume cursor。context window 只是派生视图。
Harness Runtimerun / pause / resume / wake、context builder、provider call、tool loop、guard、stream events。
Sandbox隔离执行、可写根、进程生命周期、credential proxy；token 默认不进 agent 可读环境。
Orchestration APIhost 挂载 runtime、注册 hands、订阅 facts、调度后台任务，但不拥有 session 语义。

重构顺序

1. 定义 runtime 接口不移动大文件，先让边界可编译：host、session、hands、events、approval。
2. Session 语义收口SDK 成为唯一 durable turn state；Claw 不再修补 pending/reconnect。
3. Hands/MCP 收口tool lifecycle、lazy start、status、sandbox policy 进入 SDK hands。
4. Claw 降级为 hostAgentManager 只做配置、auth、REST/WS bridge、facts projection。
5. Contract 去重Claw contracts 只定义 UI transport；domain schema 从 SDK 导出。

核心原则

  • 先写后读：发给 LLM 的 messages 必须先写入 messages.json，再从文件读出构造 provider 请求。
  • 事件追加：运行过程、工具调用、安全决策、compaction、provider usage 追加到 events.jsonl，不反向替代 provider context；zSessionEvent 是 JSONL 读写 schema，坏事件不能进入或污染恢复流程。
  • 根目录由宿主选择，内部结构由 SDK 规定：宿主只传 AgentHome(root)；sessions/、skills/、.mcp.json、AGENTS.md、MEMORY.md、agent.json 等子路径都由 SDK 统一维护。
  • 不做隐式迁移：agent.json 存在时直接作为事实源读取；初始化 seed 只用于首次创建，不再为已有 agent home 做 back-fill/legacy 修补；zAgentMetadata 是读写 schema，未知产品字段会被拒绝，不能混进 SDK agent home。
  • agent boot 有内部边界：home 校验、prompt pack/system prompt、agent.json seed/read、provider runtime、session store、event log、memory/project/workspace data 初始化集中在 agent-helpers/boot.ts；构造函数只接线和注册运行期能力。
  • agent config 是独立事实源：agent-config-types.ts 定义 AgentConfig/AgentCreateConfig；agent-helpers/create-config.ts 只负责 Agent.create() shorthand 到完整 AgentConfig 的转换。
  • agent runtime contract 是独立事实源：agent-runtime-types.ts 定义 query/delegate/middleware/status/event/result；事件、middleware 和 turn options 不再混在配置类型里。
  • session 数据契约是独立事实源：session-types.ts 定义 Session、metadata、todo 和 SessionStore；FileSessionStore 用 SDK-owned message/session metadata schema 校验 messages.json 与 metadata.json；产品只通过 SDK API 读取 session view，不复制 messages/events 存储语义。
  • workspace data 有内部边界：memory、workspace instructions、project knowledge 的 path/error/bytes 处理集中在 AgentWorkspaceData；Agent 只暴露 API，不复制文件布局细节。
  • runtime context 有内部边界：project context、agent instructions、skill index、runtime todo/sleep tools、allow-list 和 deny-list 解析集中在 agent-helpers/runtime-context.ts。
  • run state 有内部边界：status、pause abort、sleep wake、interject 队列集中在 agent-helpers/run-state.ts；Agent 只把这些能力接到 turn lifecycle 和 agent-helpers/runtime-tools.ts。
  • managed runtime 是宿主边界：ManagedAgentRuntime 承载 session/send/delete、pause/interject、快照、prompt/memory/project 编辑、approval event 和 hand 挂载；宿主不应通过 runtime 绕到裸 Agent 内部。
  • runtime builder 是装配边界：@berry-agent/runtime 拥有 provider resolver、context window、execution environment provider、local workspace hand、file memory、managed safety guard、observe collector、environment prompt 和 skill loadout 的组合规则；宿主只传根目录、registry、credentials、observer、安全配置、host tools 和执行位置策略。
  • runtime registry 是挂载边界：ManagedRuntimeRegistry 管 live runtime 的 mount/drop/replace/clear 和 destroy 顺序；drop() / replace() / clear() 是可等待 teardown，hand、memory provider 和 execution environment 释放完成后才报告 mount 已删除；产品层可以选择 agent id 和配置，但不再手写第二套 runtime cache 生命周期。
  • runtime supervisor 是运行所有权边界：ManagedRuntimeSupervisor 把 RuntimeOrchestrator 的 durable lease/wake facts 与 ManagedRuntimeRegistry 的 live mount 连接起来；host 只传 agent entry 和 factory，SDK 负责 acquire/reuse/renew/stop/release、wake schedule/claim 以及 orchestration 文件路径事实源。
  • wake scheduler 是后台唤醒边界：ManagedRuntimeWakeScheduler claim due wakes、调用 host handler，并把 wake 标记为 completed 或 failed；claimDueWakes({ staleClaimedMs }) 会把崩溃后遗留的 stale claimed wake 重排队并递增 claimAttempts，产品层不应再维护第二套后台 job table。
  • 减少样板代码优先使用成熟 schema 库：SDK 已采用 zod 作为运行时 JSON 校验和 TypeScript 类型推导的事实源；新增持久化/transport/domain 数据结构时，优先写 z* schema 并从 schema 推导类型，避免像 Lombok 式代码生成、decorator 魔法或手写 required/optional parser 形成新的隐式构建链；runtime orchestration、SDK config、models registry、MCP raw config、project safety、observe query、team worklist tool input 和 prompt-pack manifest 已按这个方向收敛；所有源码 import zod 的发布包必须把它声明在 dependencies。
  • 执行环境是 brain/hands 的边界：ExecutionEnvironment 描述 local、OS sandbox、container、remote runner 的 command executor、额外 hands、状态和 isolation policy；ExecutionEnvironmentProvider 从 AgentScope、WorkspaceBinding 和 ExecutionIsolationPolicy 供给具体环境；ExecutionEnvironmentRegistry 管多个 runner 的状态、drop()/replace()/disposeAll() 和 all-settled 释放；AgentScope 只提供 workspace/project 权限事实，不再假装生成 sandbox config。
  • 命令环境默认无密钥：createCommandEnvironment() 是 shell/sandbox/MCP stdio 的唯一默认 env 事实源，只复制 PATH/HOME/TMP/LANG 等基础变量；长期 provider/API key 留在 CredentialStore，credential 文件必须是非空字符串字典，只有 host 显式传入 scoped env 时才进入 runner。
  • lifecycle teardown 有内部边界：destroy 时的 active turn abort、hand dispose、memory provider dispose、execution environment destroy hook 和 capability map 清理集中在 SDK runtime/lifecycle；Agent.destroy() 与 ManagedAgentRuntime.destroy() 都返回 promise，宿主必须 await，不能 fire-and-forget；持久多 agent 拓扑属于 @berry-agent/team。
  • compaction orchestration 有内部边界：turn-entry soft/hard、inference 前 hard、prompt-too-long retry、memory flush 和 middleware hook 集中在 agent-helpers/compaction-coordinator.ts；Agent 主循环只决定何时进入 provider/tool 阶段。
  • compaction pipeline 有内部边界：compaction/types.ts 拥有 compaction config/layer/strategy 契约；compaction/runner.ts 拥有阈值判断、pre-compact memory flush 和单次 run 编排；compaction/compactor.ts 只负责编排 layer 顺序和 token 统计；compaction/layers.ts 拥有每一层消息转换与 summarize fork 逻辑。
  • provider runtime 有内部边界：初始 provider 解析、model ref 解析、host modelResolver 和 ProviderResolver 的纯规则在 agent-helpers/provider-runtime.ts；运行期 provider/config 变更、resolver refresh、error report 和 provider call 统一在 agent-helpers/provider-controller.ts，Agent 不直接持有多套 provider 事实。
  • provider contract 是独立事实源：provider-types.ts 定义 provider config/resolver/request/response/usage/stream；模型注册和 provider adapter 不再依赖混合类型桶里的隐式约定。
  • provider secret 不进入快照：ProviderConfig 只给 provider runtime 内部使用；Agent.currentProvider、ManagedAgentRuntime.currentProvider 和 AgentSnapshot.provider 只返回 ProviderPublicConfig，用 apiKeyConfigured 表达状态，不暴露 apiKey。
  • provider adapter 不做空壳转发：OpenAI/Anthropic runtime class 只负责 SDK 调用与 streaming 生命周期；wire message、tool schema 和 response 解析在 providers/*/messages.ts 与 providers/*/response.ts；model 返回的 tool input 必须在 provider 边界被规范化为对象，数组/原始值保留为 _raw，不能直接伪装成可信 Record。
  • 外部输入先窄化：provider retry error、credential file error、session file-store error、Anthropic usage、Skill frontmatter、classifier response block 都必须先从 unknown 窄化；SDK 核心运行时路径不接受 any 作为边界捷径。
  • provider middleware 有内部边界：API before/after/error hook 调度集中在 agent-helpers/middleware.ts，主 Agent loop 和 delegate loop 共用同一语义。
  • 能力注册有内部边界：memory provider tools、constructor tools、runtime addTool() 和 hands 到 model-visible tools 的 collision/check/register/unregister 集中在 agent-helpers/capabilities.ts；裸 tool 入口会被包成 SDK-owned Hand，推荐 host 使用 addHand()/removeHand() 管理执行面；runtime removeTool() 是可等待生命周期 API，会释放 backing hand；tool registration 可以提供 dispose()，由 hand teardown 统一调用；hand registry 批量释放会尝试所有 disposer 后再报告首个错误。
  • 内置 agent tool 有内部边界：load_skill 与 delegate 的注册集中在 agent-helpers/builtin-tools.ts，构造函数只组装 SDK runtime。
  • turn lifecycle 有内部边界：destroy check、memory readiness、resolver reset、session resolve、query_start/user_message、pause/error 收尾集中在 agent-helpers/turn.ts；Agent.send() 只接入依赖。
  • turn harness 有内部边界：provider request、prompt-too-long recovery、tool loop、usage/session checkpoint、messages_snapshot 集中在 agent-helpers/query-loop.ts；Agent 只负责生命周期入口和依赖注入。
  • message repair 只有一条路径：orphan tool_use / displaced tool_result 修复集中在 message-repair.ts；session resume 和 event-log recovery 不再各自维护修复逻辑。
  • tool execution 只有一条路径：主循环和 delegate 都走 agent-helpers/tool-executor.ts 的 executeTools()；guard、middleware、unknown tool、error result 和事件投影不再维护两份实现，也不作为 public API 暴露给宿主；team/worklist tool input 在 SDK team 边界校验，非法状态不会写入持久 worklist。
  • tool contract 是独立事实源：tool-types.ts 定义 tool group、registration、result、guard context/decision；public index.ts 直接从窄契约导出。
  • session view 属于 session 层：SessionController 负责 AgentSessionView hydrate、session list summary 和 appendSessionEvent；手动压缩入口委托给 agent-helpers/session-compaction.ts，产品和 Agent 都不应重建 UI history 或压缩流程；zSessionEvent 也校验 query/delegate result 与 token usage payload，timeline 不是任意 JSON 垃圾桶。
  • content/message 是独立事实源：content-types.ts 定义 SDK canonical ContentBlock/Message，provider adapters、schema、chat view 和 public index.ts 都围绕它转换/导出。
  • chat 契约和转换分离：chat-types.ts 定义 SDK session/chat view 类型，chat-schema.ts 只承载 zod 校验；chat-blocks.ts 拥有 content block 文本/预览转换，chat-timeline.ts 拥有 live/session timeline event 投影，chat-messages.ts 拥有 messages/events 到 UI message 的 hydrate 与标题推导，chat.ts 只保留 AgentSessionView 对外装配入口。旧 toChatMessages()/toChatTimeline() 兼容层已删除。
  • 项目共享目录由 SDK 规定：projectSharedPaths(project) 是 AGENTS.md、.berry/team.json、.berry/messages.jsonl、.berry/worklist.json、.berry/safety.json 的唯一路径事实源。
  • 不放产品逻辑：团队工作台、服务器切换、手机/桌面连接、ClawHub 市场 UI 等属于产品端。
  • PromptPack 是 SDK 能力：基础行为、压缩摘要、记忆 flush、handoff/resume 统一由 @berry-agent/prompt-pack 管理。

代码规范

  • 不引入无事实源的缓存；缓存只允许作为明确可丢弃的派生状态。
  • 魔法值必须集中维护，优先使用常量、枚举或 schema。
  • 序列化/反序列化必须标明事实源，不能让前后端各自维护一份漂移结构。
  • 新增 SDK API 时必须明确：输入事实源、输出事实源、是否持久化、是否影响 provider context。
  • 测试覆盖随风险增加：provider/session/compaction/event log/safety 变更必须有单测。
